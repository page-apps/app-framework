# App Framework — Agent-Produced Public Reader

Status: Accepted
Date: 2026-09-20
Decision ID: ADR-003

> See [the pattern catalogue](PATTERNS.md) for the implementation rules and the distinction from the fixed-private-data pattern.

## Context

Some Page Apps are readers rather than editors. A local machine, scheduled worker or coding-agent host periodically researches and writes content, while the user only needs to open a public Pages site and read the released material. AI Daily is the concrete example: the agent creates editorial bundles privately, and stable daily and news documents are promoted into the public reader repository.

The existing fixed-private-data pattern is not sufficient for this use case. It requires a browser-held PAT and runtime reads from a private repository. That is appropriate for private personal data, but it does not provide an anonymous public viewer. A private repository cannot be both the direct data source for an anonymous Pages site and remain private.

## Decision

Add an **agent-produced public reader** pattern with two explicit repository boundaries:

```text
private editorial repository
  drafts, research, prompts, provenance, review history
          │ validated public-safe promotion
          ▼
public reader repository
  reader source, released content, public Pages workflow
          │
          ▼
anonymous public viewer
```

The private repository is the producer/editorial boundary. The public repository is the publication boundary and the only content source used by the public Pages build. The public reader does not fetch the private repository at runtime and does not require a PAT.

The publisher must:

- create versioned and reproducible drafts;
- run deterministic checks and any required human or independent-agent review;
- promote an explicit release set, not an entire private checkout;
- validate the public release again in the public repository;
- make retries idempotent and stop on conflicting content for the same release key; and
- keep private prompts, credentials, unpublished drafts, hidden research context and agent state out of public commits, logs, URLs and Pages artifacts.

The public workflow owns build and deployment status. A private editorial commit is not a publication event. The release is visible only after the public commit is accepted and the Pages deployment succeeds.

## Consequences

### Positive

- Readers get a simple anonymous, static and cacheable viewer.
- Agent credentials and unpublished editorial material remain outside the public repository.
- Git history provides an inspectable release trail on both sides of the boundary.
- The generator can run locally, on a scheduler or on a separate worker without coupling the browser to the producer.
- A failed review or private generation run does not change the public site.

### Negative

- Public content must be copied or promoted into a second repository before it is visible.
- Private and public commits are not one atomic Git transaction; recovery and idempotency are required.
- Anything promoted is public, including rendered HTML, JavaScript, source maps, indexes and URLs.
- The pattern does not provide anonymous access to private drafts. That requires the fixed-private-data or authenticated-workspace pattern and a PAT.

## Rejected alternative

Use the public Pages app to fetch the private editorial repository directly. Rejected because a static anonymous browser cannot authenticate to a private repository without exposing a credential or adding a backend. If the repository remains private, the viewer must be authenticated; if the viewer is anonymous, the released content must be public.
