# Repo Apps Harness — Public Shell and Private Data Repository

Status: Accepted
Date: 2026-08-12
Decision ID: ADR-002
Amends: ADR-001 sections 2–5 and related implementation guidance

## Context

The original design assumed that a static GitHub Pages app would normally read and write the repository that built and deployed it. It also kept GitHub Device Flow as a planned browser credential provider and treated persistent, same-origin PAT reuse as a primary convenience feature.

Testing the production Pages deployment exposed three problems with that model:

- GitHub's Device Flow and token exchange endpoints under `github.com/login/` do not provide the browser CORS contract required by a static Pages application. Device Flow is intended for constrained or headless clients such as CLIs.
- A PAT with `Contents: write` access to the repository that publishes the app can also modify the code that will later receive that PAT. Client-side path restrictions do not reduce the token's underlying GitHub permission.
- Apps under project paths such as `https://page-apps.github.io/quick-log/` share one browser origin. Persisting a token in `localStorage` makes it readable to any compromised script running under that origin, regardless of path.

GitHub's REST API at `api.github.com` does support browser CORS. A static app can therefore access a private repository when the user supplies an appropriately scoped PAT at runtime, without embedding a secret in the Pages build.

## Decision

### 1. Add a public-shell/private-data topology

The framework supports two data-repository modes:

1. `self`: canonical data and the Pages application are in the deployment repository.
2. `fixed`: the public Pages application is built from one repository and canonical data lives in one explicitly declared repository, which may be private.

A fixed target is public, token-free build configuration:

```ts
repository: {
  mode: "fixed",
  owner: "page-apps",
  name: "bookmark-data",
  branch: "main",
  dataRoot: "data",
}
```

The target must be declared in the app manifest. It must not come from a query string, URL fragment, arbitrary user input or mutable browser storage. This keeps the app's repository capability narrow and auditable.

The runtime configuration identifies both boundaries:

- the deployment repository that produced the Pages artifact; and
- the canonical data repository used by the repository client.

For personal apps containing private information, the recommended layout is a public application repository plus a separate private data repository. The PAT selects only the private data repository and grants only `Contents: read and write`.

### 2. PAT is the only static-browser authentication method

Generated Pages apps support fine-grained PAT entry at runtime. Browser Device Flow is removed from the supported framework contract.

No PAT may be placed in source control, an Actions variable or secret exposed to the build, generated JavaScript, a URL, a service worker, telemetry or logs. The browser sends it only to the GitHub REST API through the shared repository client.

If a future app needs a conventional GitHub sign-in experience, it must use a separately reviewed backend or serverless credential broker and a GitHub App or appropriate OAuth flow. That is a different deployment architecture and remains outside the static framework.

### 3. Session storage is the default

The default credential lifetime is the current tab session. Memory-only storage is also supported.

Persistent `localStorage` remains an explicit, disclosed opt-in for a trusted personal device. Same-origin shared PAT storage is not enabled in generated apps by default and is not the recommended topology. A custom domain on a separate origin is recommended when an app needs stronger isolation from other Pages apps.

Disconnect must remove the active app credential. Applications that persist credentials or private offline data must also provide a clear-local-data action.

### 4. Private responses are runtime data, not Pages assets

A Pages build for a fixed private data repository includes schemas and demo fixtures only. It must not download canonical private data and place it in the Pages artifact.

Service workers may cache versioned public application assets. They must not cache authenticated GitHub API requests or responses. An application may deliberately store private records in IndexedDB for offline personal use only when the UI discloses that local copy and can delete it.

### 5. Use two independent Actions pipelines

Separating the repositories does not remove GitHub Actions. It creates two pipelines with different responsibilities:

```text
Public app repository                 Private data repository
source change                         PAT data commit
→ test/type-check                     → schema validation
→ build PWA                           → generate private indexes/summaries
→ deploy GitHub Pages                 → mark the data revision ready
```

The installed PWA reads canonical and generated private files through `api.github.com` with the PAT. No private artifact is copied into the public Pages deployment.

In `self` mode, a canonical-data commit may trigger the same repository's validation and Pages deployment, so `committed → building → published` remains meaningful.

In `fixed` mode, a data commit triggers the private repository's data workflow but does not rebuild the public shell. When a data workflow is declared, the lifecycle is `committed → validating → data ready` (or `validation failed`). Tracking that workflow requires optional `Actions: read` access; saving itself still requires only `Contents: read and write`. If workflow tracking is disabled or unavailable, the app reports the commit as saved and links to it without claiming validation or Pages publication.

Generated private artifacts should be deterministic and stored under a declared derived-data root such as `generated/`. A workflow may commit those artifacts with its repository-scoped `GITHUB_TOKEN`; the app treats canonical files as authoritative and generated files as replaceable. The workflow must use path filters or commit guards to avoid recursively triggering itself.

## Consequences

### Positive

- The public app can remain inspectable and inexpensive while canonical personal data stays private.
- The data PAT cannot modify the application repository when it is scoped only to the private data repository.
- Static hosting remains viable because authenticated REST API calls support browser CORS.
- Most apps need only one fine-grained permission: repository Contents read/write.
- Data changes appear on the next runtime read without waiting for a Pages deployment.
- Private data still benefits from schema checks, generation, audit history and visible workflow failures.

### Negative

- A browser-held PAT is still a bearer credential exposed to XSS, compromised dependencies, browser extensions and malicious same-origin code.
- A separate private repository adds setup and repository-management work.
- Runtime data cannot be pre-rendered into the public artifact.
- Live data-workflow status adds the optional `Actions: read` permission.
- Offline private data requires an explicit local-storage lifecycle.
- A polished OAuth or GitHub App sign-in requires a backend component and is outside this framework.

## Security disclosure requirement

Every connection screen must communicate the following meaning before persistent storage is enabled:

> This personal app uses a GitHub token in your browser to access its configured data repository. A security flaw in this app, a dependency, a browser extension, or another app on the same origin may expose the token and locally cached private data. Use a fine-grained, expiring token limited to the displayed repository and minimum permissions. Session-only storage is recommended.
