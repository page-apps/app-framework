# App Framework — Scheduler Contract for Agent-Produced Readers

Status: Accepted
Date: 2026-09-20
Decision ID: ADR-004
Extends: ADR-003

## Context

ADR-003 defines the private-editorial/public-reader publication boundary, but it does not define how recurring agent runs are identified, locked, retried, promoted or reconciled. Existing generated-reader scripts demonstrate useful failure cases, but they are examples rather than compatibility targets.

A scheduler may run on a personal workstation, in GitHub Actions or on a dedicated worker. Those hosts have different trigger and locking mechanisms, but they need the same correctness and security rules. Scheduling cannot run in the anonymous Pages client because generation and publication require private repository, model and source capabilities.

## Decision

Add a host-neutral scheduler contract in `@repo-apps/scheduler-contract` and document it in `SCHEDULER.md`.

The contract distinguishes:

- a stable `jobId` for one independently retryable output pipeline;
- an `occurrenceKey` for one deterministic scheduled slot;
- an `executionId` for the logical execution of that slot;
- an incrementing `attempt` for retries of the same run;
- a `releaseKey` for one public content slot;
- a SHA-256 `digest` for the exact allowlisted public files; and
- public commit, workflow and deployment identities observed after promotion.

The scheduler manifest and run records are private host-side configuration and state. The existing public `repo-app.config.ts` remains free of scheduler commands, private repository paths and credentials.

The framework owns the normative run lifecycle, retry classifications, release schemas and reconciliation rules. Applications continue to own generation, domain validation, editorial policy and model selection. Hosts continue to own clock triggering, process execution, secret injection and one durable lifecycle authority.

This is a greenfield contract. The framework does not preserve or migrate existing chained shell commands, draft layouts, status names or publication scripts.

Every adapter must establish single-owner execution before mutation. Store-backed adapters use a lease with a fencing token. Durable workflow engines may instead use workflow identity, overlap policy and workflow history as the execution and state authority. Because neither mechanism makes orchestration and Git transactional, the final publication boundary is an expected-head public repository commit plus release-key/digest reconciliation. The same release key and digest is an idempotent success; the same key with another digest is a conflict.

Temporal is a supported adapter profile. The contract `executionId` maps to Temporal Workflow ID, not Temporal Run ID. Workflow history replaces the mandatory external run store, side effects run as idempotent Activities, and Signals or Updates may complete review. Temporal-specific schedule configuration remains private adapter configuration through the portable `external` trigger. See `TEMPORAL.md`.

A run becomes `published` only after the observed Pages deployment corresponds to the promoted public commit. A private draft commit or public promotion commit alone is not publication.

## Consequences

### Positive

- Local cron and GitHub Actions can share one lifecycle and recovery model.
- Retries cannot silently create another logical release.
- Public promotion can be recovered if the private close-out step fails.
- Safe public release metadata is separated from private paths and editorial details.
- Application-specific agent logic remains outside the framework core.

### Negative

- Hosts still need an adapter and one durable state authority; the framework is not a hosted scheduler.
- Cross-repository promotion remains non-atomic.
- Lease or durable-workflow ownership reduces duplicate work but does not replace the final public branch compare-and-swap.
- Existing generated-reader apps must adopt release manifests before they receive full reconciliation guarantees.

## Deferred

- A hosted scheduler service or database-backed run store.
- Multi-job DAG orchestration.
- Cross-job resource locking or quota coordination.
- Cross-host distributed locks beyond leases plus repository compare-and-swap.
- Generic model, prompt or human-review orchestration.
- Browser control of privileged scheduler runs.
- Compatibility adapters or migrations for pre-contract schedulers.
