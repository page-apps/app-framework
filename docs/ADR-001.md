# Repo Apps Harness — Architecture Decision Record

Status: Accepted for the original MVP; authentication, persistence and data-repository sections amended by ADR-002
Date: 2026-08-11
Decision ID: ADR-001

> See [ADR-002](ADR-002.md) for the current public-shell/private-data topology, PAT-only static-browser authentication contract and session-first credential policy.

## Context

We want to create many small personal applications with coding agents. These applications should be inexpensive to host, predictable to generate, easy to inspect and based on user-owned data. We also want an optional parent hub that can present and coordinate several child applications without flattening their boundaries or allowing routine parent updates to modify them accidentally.

GitHub provides the required primitive services:

- GitHub Pages can host a static application.
- GitHub repositories can hold versioned canonical content.
- GitHub REST APIs can read and mutate repository content.
- GitHub Actions can validate, transform, build and deploy after a commit.

The approach has known limits: browser token exposure, API rate limits, build latency, weak same-origin isolation, Git merge conflicts and the absence of database transactions or real-time collaboration. These limits are acceptable because the project targets personal, low-frequency applications and will disclose the risks rather than claiming enterprise-grade security.

## Decision

We will build an opinionated Repo Apps Harness with the following architecture.

### 1. Fixed platform

- Astro is the only supported application shell for the initial version.
- TypeScript is the implementation language.
- GitHub Pages is the only supported host.
- GitHub Actions is the only supported build and deployment pipeline.
- GitHub REST and Git Data APIs are the remote content interfaces.
- A shared library owns authentication adapters, GitHub access, runtime state, validation, conflict handling and common UI.

The initial project will prefer predictable conventions over framework neutrality.

### 1.1 Supported repository topologies

We support two explicit topologies:

1. **Standalone:** one app owns one repository, one canonical data boundary and one Pages deployment.
2. **Hub:** one parent app owns the repository root; child apps live exactly one level below `apps/<app-id>/`.

The standalone topology remains the MVP and default. Hub mode is an additive composition model, not a central database model. The parent may discover and present child metadata, links or explicitly permitted summaries. It may not silently assume write access to child data.

The one-level folder rule is an architectural boundary for agents and automation. Root paths are parent-owned. `apps/<app-id>/` is child-owned. Routine parent maintenance excludes `apps/**`; a child change requires an explicitly scoped task.

### 2. Closed application loop

Every application follows the same lifecycle:

```text
Open Pages app
→ Demo mode or connect credential
→ Read repository data
→ Render application
→ Edit locally
→ Validate
→ Commit to repository
→ Trigger GitHub Actions
→ Build and deploy
→ Observe published version
```

`Committed` and `Published` are separate states. A successful GitHub commit does not imply that the new Pages deployment is already live.

### 3. Canonical and derived state

State is divided into four categories:

| State | Location | Authority |
| --- | --- | --- |
| Canonical app data | GitHub repository | Authoritative |
| Local draft/cache | Browser storage | Temporary |
| Generated indexes/build output | GitHub Actions artifact / Pages | Derived |
| Credential | Memory, localStorage or scoped cookie | User-controlled but exposed to browser risk |

Generated output must not be treated as canonical data. GitHub Actions should regenerate indexes and site artifacts from repository source.

In hub mode, the same rule applies per child. The parent may maintain a derived catalogue or index under its own root, but child data remains authoritative in the child's declared data root. A parent-generated summary is never a replacement for child canonical data.

### 4. Authentication (amended by ADR-002)

The original decision planned both a fine-grained PAT and GitHub Device Flow. ADR-002 replaces that plan: fine-grained PAT entry is the only authentication method supported directly by a static browser app. Device Flow requires GitHub login endpoints that do not provide the necessary browser CORS contract and is not appropriate for a Pages SPA.

Application modules receive a repository capability, not the raw token. The shared credential provider is the only supported application-level path to a credential.

This is source-code discipline, not a browser security boundary. Any same-origin script may still be able to obtain browser-stored credentials if the site is compromised.

### 5. Credential persistence and sharing (amended by ADR-002)

The shell may support:

- Memory-only or session credential.
- Persistent credential in `localStorage`.
- Explicitly opted-in persistent credential in `localStorage`.

We explicitly acknowledge:

- `localStorage` is isolated by origin, not app path.
- Cookie `Path` does not provide strong protection from malicious same-origin JavaScript.
- Multiple project sites under `https://user.github.io/...` share an origin.
- One token reused across many apps is convenient but expands the impact of token theft.

Therefore session storage is the default. Persistent and same-origin shared credentials are compatibility features for trusted personal devices, must be explicit, disclosed and reversible, and are disabled in generated apps by default. Fine-grained PATs should have the narrowest practical repository scope, permissions and expiry.

### 6. Demo mode

Every app must remain useful without authentication.

Without a credential, the app loads bundled fixture data or a configured public snapshot and clearly identifies itself as read-only demo mode. Demo writes may update temporary in-browser state for demonstration, but must never call privileged GitHub APIs or imply that changes were persisted remotely.

No privileged token may be embedded in the app to power demo mode.

### 7. Write and conflict model

- Small normal edits commit directly to the configured branch.
- Updates include the expected current SHA or equivalent revision.
- A revision mismatch becomes an explicit conflict.
- The default conflict policy is `prompt`; silent overwrite is forbidden.
- Multi-file atomic changes may use Git Data APIs.
- Schema migrations and high-risk generated changes should use pull requests in later versions.
- Per-keystroke commits are forbidden; apps commit explicit or batched user changes.

### 8. Application generation boundary

Coding agents may generate or modify:

- App manifest.
- Data schemas.
- Demo fixtures.
- Domain components and views.
- App-specific Actions steps.
- Tests and documentation.

Coding agents should not modify without an explicit framework task:

- Credential storage implementation.
- Token redaction rules.
- Core GitHub request logic.
- Conflict semantics.
- Runtime state machine.
- Security disclosure.
- Shared deployment workflow contracts.

Generated application code must use the shared library rather than implementing direct GitHub API calls.

For hub repositories, generation and maintenance are scope-aware:

- parent tasks target root paths by default;
- child tasks target one named `apps/<app-id>/` path;
- scripts must use explicit allowlists or path filters when updating files;
- parent scripts must not bulk-format, migrate or rewrite child folders; and
- a hub build may invoke child validation/build steps only as explicit, named jobs.

## Consequences

### Positive

- Very low hosting and operational cost.
- User owns source and application data.
- Git supplies history, auditability and rollback.
- Actions provides asynchronous validation and generation.
- A coding agent works within a small, deterministic capability surface.
- Fixed conventions make applications easier to generate, understand and repair.
- Demo mode makes every app viewable before credential setup.
- Apps can optionally reuse a credential on the same origin.

### Negative

- Browser-held PATs and user tokens are vulnerable to XSS, compromised dependencies and same-origin apps.
- GitHub Pages cannot securely hold application secrets.
- Browser-held PATs require deliberate expiry, repository scoping and storage choices.
- Shared tokens increase the security blast radius.
- GitHub API rate limits constrain polling and frequent writes.
- Repository operations have higher latency than a local database.
- Actions and Pages deployments are eventually consistent, not immediate.
- Git does not provide general database transactions or realtime collaboration.
- Repositories and histories may grow if apps commit too frequently.
- GitHub Pages cannot provide configurable server-side security controls for the application.
- A hub adds composition and release coordination complexity.
- Embedded child apps may share the hub's deployment and failure domain unless separately deployed.
- A parent credential with several child capabilities can have a wider blast radius than a standalone app credential.

## Alternatives considered

### Framework-first, backend-neutral platform

Rejected for the initial version. Supporting multiple hosts, frameworks and storage backends would make AI generation less predictable and introduce abstractions without validated personal use cases.

### Application-only implementation

Rejected. Reimplementing PAT handling, repository access and conflict behaviour in every generated app would create inconsistent security and reliability.

### Hosted backend and database

Rejected for the initial personal-use goal. It would improve authentication and data access but add deployment, ownership and operational complexity that this pattern is intended to avoid.

### GitHub App with private backend

Deferred. It is the stronger choice for a public multi-user product, but the current project explicitly targets personal use and accepts the limitations of a browser-held PAT.

### One isolated origin per app

Not required. It offers better isolation but prevents the convenient same-origin shared-token model. Individual apps may still choose a custom domain when isolation matters.

### Monolithic parent application with flattened child data

Rejected. Flattening child data into the parent would make the hub convenient initially, but would destroy ownership, schema and migration boundaries. The hub should compose child applications, not become the canonical database for them.

### Arbitrarily nested child-app folders

Rejected. More nesting makes path-scoped agent instructions, build filters, deployment discovery and safe update scripts ambiguous. Child implementation folders may be deep, but peer applications must remain at `apps/<app-id>/`.

## Security disclosure requirement

Every generated app must show or link to a standard disclosure before persistent credential storage is enabled:

> This personal app stores a GitHub credential in your browser. A security flaw in this app, one of its dependencies, or another app on the same origin may expose that credential. Use a fine-grained, expiring token limited to the minimum repositories and permissions. Do not use this design for sensitive multi-user applications.

The disclosure is part of the product contract and must not be removed by generated apps.

## Implementation guidance

Build the first vertical slice in this order:

1. Astro shell and demo fixture.
2. Credential-provider interface.
3. Session-only PAT provider.
4. Repository read.
5. Local edit and validation.
6. Revision-aware commit.
7. Conflict UI.
8. GitHub Actions build and Pages deployment.
9. Committed/building/published status UI.
10. Optional PAT persistence.
11. Optional fixed private-data workflow tracking.
12. Shared same-origin credential vault.
13. Hub manifest and one-level child-app discovery.
14. Parent catalogue/composition view.
15. Scoped child validation/build jobs and safe update tooling.

Do not build a general app generator until the Quick Log reference app completes the full loop.

## Review triggers

Revisit this ADR if any of the following becomes true:

- The project supports untrusted users or public writes.
- Apps store materially sensitive data.
- A compromised app must not affect other apps on the same origin.
- GitHub removes or materially changes fine-grained PAT or browser REST API support.
- Write frequency regularly approaches GitHub API limits.
- Applications require realtime collaboration or transactional multi-record updates.
- A backend becomes acceptable for authentication or token brokerage.
- The hub needs unscoped writes across child applications.
- Child applications require arbitrary nesting or independent deployment rules that conflict with the one-level boundary.
- The parent must become the canonical data store for child applications.
